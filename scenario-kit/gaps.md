# すき間の説明(書き方の一覧には出てこない決まり)

外からシナリオを作った人(とエージェント)が実際につまずいた所を、答えと一緒にまとめた。

## 階の決まり

- B1 には上り階段 `u` が要る(町へ戻る道)。最下層以外の階には下り階段 `d` が要る。最下層の上り階段 `u` も要る(上の階へ戻る)。
- 迷宮に入ると、B1 の上り階段 `u` のマスに着く。地図の `start x y 向き` は、着いたときの向きと、上り階段が無いときの着く場所に使う。`start` が階段と同じマスや隣でも問題ない。
- 階段で着く場所は、行った先の階の階段(下りたら `u`、上ったら `d`)。上下の階で座標をそろえる必要はない。階段は1つずつにする(2つ以上あると、着くのは見つけた1つ目だけ)。
- 終わり方は2つ: 最下層に主(`mark x y boss:final` と `bosses.json` の `final`)を置いて倒すか、イベントの手順 `ending` で終える。
- 錠のある扉(`L`)の階には、鍵(`mark x y key`)を置く。鍵だけで錠が無い階は、拾えるだけで何も開かない。
- 門は、印 `gate:<id>` のマスの周りの `L` で、鍵では開かず、イベントの手順 `open` で開ける。`L` は2つのマスのあいだの辺なので、印は `L` の両側どちらのマスに置いてもよい。ただし印のマスに `L` が接していないと、開けても何も変わらない(`check` が注意する)。
- `open` は、そのイベントが起きた階の門だけを開ける。スイッチと門は同じ階に置く(別の階なら `check` が注意する)。
- `room x y w h` の部屋は、階に入ったときに `encounters.json` の `room_chance`(省くと 0.35)の割合で敵が待つ。

## 階の名前と入ったときの文

- 階の名前と入ったときの文(`enter`)は、`worlds.json` の `floors` に書く。地図の `name.ja` / `name.en` 行は、`worlds.json` に名前が無いときだけ使う控え。
- `worlds.json` の `enter` は、地図に名前の行があっても出る。

## ボスの文

- 最下層の主(`final`)の、戦う前と倒したあとの文は、`worlds.json` の `boss.intro` / `boss.victory` が先に使われる。無ければ `bosses.json` の `intro` / `victory`(文言のキー。`text/ja.json` などに文を書く)。
- `final` 以外のボスは、`bosses.json` の `intro` / `victory` だけ。
- `worlds.json` の `boss.escorts` は、主に従う組の呼び名(主の組 `groups` の2組目から順に、1つずつ。例: 「水門の番兵」)。足りない組や空の `[]` は、元の敵の名前のまま出る。主が1組だけなら `[]` でよい。

## 散らすイベントと手で置いた印

- `standard_events: false`(manifest): 土台の標準イベントを、新しいゲームで散らさない。ただし読み込みと検査はされ、`new` のはめ込む部屋のように地図に印があれば動く。
- `events_placed: true`(dungeons.json): 散らすイベントは、もう地図に置いた分だけ。手で置いた印だけで作るときはこれ。`false` なら、新しいゲームのたびに散らす。

## 検査の数の読み方

- 「歩いたマス x / y」の差は、テレポーターとシュートのマス(乗ると移されるので、歩くボットは立たない)。`finish` が座標を出す。

## 地図の文字の位置

`size W H` の階の `walls` は (2W+1) 文字 × (2H+1) 行。マス (x, y)(左上が (0, 0)、x は右へ、y は下へ)の文字は、列 2x+1・行 2y+1。

- マスの右の辺(縦の辺): 列 2x+2・行 2y+1。マスの下の辺(横の辺): 列 2x+1・行 2y+2。
- 偶数の列・偶数の行の交わりは角で、文字は何でもよい(ふつうは `+`)。
- `mark`・`room`・`start` などの座標は、この (x, y)。

## 仕掛けの組み方

[examples/kit_example](examples/kit_example) の見本の行を指して説明する。

- **鍵と錠**: B1 の地図の `L` が錠の扉、`mark 1 0 key` が鍵。鍵を拾えば、その階の錠が開けられる。
- **フラグを立てて、あとで読む**: `kit_example_lever` の「引く」が手順 `flag` でフラグを立て、`kit_example_altar` の手順 `if` の `when` が条件 `flag` で読む。立てたのにどこでも読まないフラグは、仕掛けとしては何も変えない(`check` が知らせる)。
- **立ち去っても、また来れば選び直せる**: `once` のあるイベントは、最後まで進むと済んだことになり、もう起きない。「やめておく」「立ち去る」のような選択肢には手順 `again` を付ける(付けないと、その場で済んでしまい、報酬も取れなくなる。`check` が注意する)。条件を満たしていないときの `else` にも `again` を付けると、条件を満たしてから来れば起こる(`kit_example_altar`)。
- **門**: B2 の `mark 3 0 gate:kit_example_gate` のマスの `L` を、`kit_example_switch` の手順 `open`(id が同じ)が開ける。
- **印の文**: `mark 0 1 message:kit_example_welcome` のキーの文を、`text/ja.json`・`text/en.json` に書く。

## イベントの書き方の目安

- 手順ごとに使う項目は、[reference/events.md](reference/events.md) の `EventStep` の説明の頭(手順の種類ごとの段落)に書いてある。書いていない項目は省いてよい。同梱のシナリオの `events.json` には、省いてよい既定の値(`dc: 10`、`value: 0` など)まで書いてあるものがあるが、真似しなくてよい。
- 状態・技能・ダメージの種類の名前は `ScenarioCheck list conditions|skills|damage`、品は `list items`、モンスターは `list monsters`。
- 英語と日本語の文は、同じ内容にする。英語を一般的な文で済ませない。

## パックの重なり方

ゲームは `Content/srd`(土台)を読み、その上にシナリオのパックを重ねる。同じファイル名(例 `monsters.json`)は、同じ種類の物の一覧として足し合わされる。

| 書き方 | 意味 |
|---|---|
| 新しい id | 足す |
| 土台と同じ id | **中身ごと置き換える**(項目ごとに混ぜない。書かなかった項目は既定の値になる) |
| `"extends": "元の id"` | 元を写して、書いた項目だけ置き換える。置き換えは一番上の項目ごとで、配列や入れ子のオブジェクトは丸ごと置き換わる(配列に1つ足す、はできない。全部書く) |
| `{"id": "bard", "disabled": true}` | それまでに読んだその id を外す。一覧から消え、選べなくなる |

- 外した物を `extends` の元にはできる(ウィザードを写したクラスを作り、ウィザードは外す)。
- 外したクラスや種族を指している標準の定義は、誤りにならない。誰も持たなくなった技や能力は使われないだけで、外したクラスを条件にする標準のイベントは「当てはまらない」になるだけ。
- モンスターを `extends` で写すと、自分の絵(`art/monsters/<id>.png`)が無ければ元の絵を使う。別の絵にしたいときは `art_from` で絵だけ別のモンスターから借りる。`extends`(数値の元)と `art_from`(絵の元)は別に決まる。`ScenarioCheck art` で一覧を見て確かめる。
- 文言(`text/ja.json`・`text/en.json`)はキーごとに上書きされる(同じキーなら後のパック)。

## 標準のイベント

- 土台には迷宮に散らす標準のイベントがある。`manifest.json` の `standard_events: false` にすると散らさない。ただし読み込みと検査はされる。
- イベントの `id` が標準と同じなら置き換わる。標準のイベントを少し変えたいときは、同じ id で全部書く(イベントに `extends` は使わない)。

## 省いたときの値

項目ごとの既定は、[reference/](reference/README.md) の説明と型で分かる。型の `?` は省ける項目。説明に値が無ければ型の既定(数 0、真偽 false、一覧は空)。よく聞かれるもの:

- `encounters.json` の `room_chance`(部屋に入ったときに戦いになる確率): 省くと 0.35。
- `manifest.json` の `allow_import`(クランを連れて入れる): 省くと true。クラスを足したシナリオでは false にし、続き物なら `series` を揃える。
- イベントの `once`: 省くと何度でも起こる。`"game"` でゲームに1回、`"place"` で置いた場所ごとに1回。
- イベントの `trigger`: 省くと `enter`(マスに着いたとき)。
- `dungeons.json` の `named` の `floor`(名のある敵のねぐらの階)は 0 から数える。0 が B1、1 が B2。

## 呪文とクラス

- 呪文の効果とレベルは土台のまま。シナリオで変えられるのは名前だけ。
- クラスごとに変えられるのは: どの呪文の束を、そのクラスで何レベルの呪文として(`spell_access` の `spelllv`)、クラスの何レベルから(`lv`)使えるか。スロットの数(`spell_progressions` と `spell_slots`)。覚える数(`spellcasting.known`・`cantrips`)。
- 組み合わせの結果は `ScenarioCheck spells <クラス> --scenario <フォルダ>` で、レベルごとのスロット・覚える数・新しく使える呪文を見る。手で計算しない。
- 「全部覚える」を `known: 99` のような大きな数で代わりにしない(訓練場の画面と合わなくなる)。

## 検査の文の読み方

- 読み込みの問題の終わりに `(ファイル: srd/features.json)` のように書いた場所、イベントなら `(場所: steps[0].options[1].when[0])` のように入れ子のどこかが付く。
- `ScenarioCheck check` の `！`(注意)は、わざとなら直さなくてよい。よく出るもの:
  - 「最下層の主が迷宮にいない」: 手順 `ending` で終わるシナリオなら出ない。主をイベントの戦闘で倒すなら、そのままでよい。
  - 「使われていないイベント」: 散らさず、どのマスにも置かず、ほかのイベントの `run` や `timer` からも続かないイベント。作りかけなら置くか消す。
  - 「散らすイベントなのに迷宮に置かれていない」: 散らし直す(`ScenarioCheck fill` かエディタの「散らし直す」)。
  - 「選ぶとイベントが済んで、もう起きない」: 上の「立ち去っても、また来れば選び直せる」。
  - 「上り階段が 2 つある」: 階段は1つにする。
  - 「門 X のマスに錠の辺(L)が無い」: 印を `L` の隣のマスへ動かすか、`L` を足す。
  - 「open X は、門のある B? を開けない」: スイッチのイベントを門と同じ階に置く。
  - `・` 「フラグを立てているが、どの条件でも読んでいない」: 記録だけならそのまま。仕掛けのつもりなら、条件 `flag` で読む。
  - `・` 「仕切りの無い1部屋」: 迷宮らしくするなら壁や扉を足すか、`ScenarioCheck new` の迷宮から始める。
  - 「worlds.json の id が、シナリオの id と違う」: `worlds.json` の `id` をシナリオの id(manifest の id)にする。
  - 「worlds.json に雛形のままの文(TODO で始まる)」: `new` が書いた雛形。書き換えるか、要らない項目を消す。
- `×` 「歩いて行けないマス」に「手前で開かない錠の辺(L)がある」と添えてあるときは、門の印 `gate:` も、その階の鍵 `key` も無い `L` が残っている。標準の部屋の印を外して `L` だけ残したときによく出る。`L` を壁か通路にするか、門の印を戻す。
- ボットの「クリアできなかった理由」は括弧の中に、どの階で、誰が動けず、持ち金がいくらだったかが付く。

## ボットについて

- `check --bots` のボットは、決まった手順で潜って戻ることを繰り返す単純なプレイヤー。クリアできないことだけで、迷宮や敵の強さが間違いとは限らない。全滅の回数・届いた階・理由を見て判断する。
- 強さの手触り(一戦ごとの緊張感など)はボットでは分からない。HP を低くするなどの変更は、呪文や罠の危険度を大きく変える。人が遊んで確かめる。

## よくある間違い

- 同梱のシナリオを写して `id`・`guid` を変え忘れる。
- イベントの印 `event:<id>` の id と、`events.json` の id が合っていない(検査が「印のイベントが無い」と出す)。
- 錠のある扉の階に鍵(印 `key`)を置き忘れる。
- 本物のセーブやシナリオのフォルダで試す(`--saves` と `--scenarios` を付ける)。
- 道具で確かめるための設定を、ゲームの機能と思い込む。ゲームが読むのは、[reference/](reference/README.md) に出ている項目だけ。
